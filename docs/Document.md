## 1. 文档目的

本文档用于记录“夜行者 / Morpheus”App 的开发目的、最终效果与大致要求，作为后续立项、设计、开发、测试和版本迭代的共同依据。

核心目标是：先明确“为什么做、做成什么样、必须满足什么要求”，再进入具体技术实现，避免范围失控。

## 2. 开发目的

### 2.1 直接目的

解决“醒来后梦境快速遗忘、记录门槛高”的问题。

用户在刚醒来时，往往还记得梦境片段，但拿起手机、打开笔记、组织语言的过程会打断回忆。夜行者希望通过智能手表睡眠数据或定时提醒，在合适的时间推送通知，让用户第一时间记录梦境。

### 2.2 产品目的

做一个低压力、私密、美观的梦境记录工具。

它不强制用户使用智能手表；没有手表或不愿授权健康数据时，也可以设置固定起床时间，每天定时提醒。记录以自由文本为主，后续再扩展字体、背景、样式等编辑能力。

### 2.3 长期目的

把梦境记录从“单次笔记”变成“可回顾、可分析、可延展的个人数据资产”。

在积累足够数据后，通过 AI 生成梦境画报、周期梦境回忆报告，并根据情节、氛围、意象推荐电影、音乐、文学作品。

### 2.4 技术验证目的

Version 0.1 首先要验证三个技术闭环：

1. 健康数据读取是否可行：HealthKit / Health Connect。
2. 通知是否能在正确时间触发：本地通知或服务端推送。
3. 本地记录与日历回顾是否顺畅：数据保存、查询、编辑、补记。

## 3. 最终效果

### 3.1 Version 0.1 最终效果

用户打开 App 后：

1. 完成通知权限、健康数据权限引导。
2. 如果有智能手表并授权，App 读取睡眠数据，在用户醒来时推送“记录梦境”通知。
3. 如果没有手表或不授权，App 提醒用户设置每天定时推送时间。
4. 用户点击通知进入记录页，输入梦境文本。
5. 文本自动保存，可在日历中按日期查看。
6. 用户可以选择过去某一天，查看或补记当天梦境。

最终交付一个能正常编译、启动、运行的双端 App，跑通“提醒 → 记录 → 保存 → 日历查看 / 补记”的最小闭环。

### 3.2 进阶最终效果

在 0.1 基础上逐步实现：

- AI 梦境画报：根据梦境文本生成图像。
- 周期梦境回忆报告：按周 / 月分析情绪、意象、重复主题。
- 智能推荐：根据梦境氛围推荐电影、音乐、文学作品。
- 云同步与多设备：账号体系、数据备份、跨设备查看。
- 更丰富的编辑器：字体、背景、样式、标签、心情、插图。

### 3.3 团队交付效果

- iOS / Android 双端可运行。
- 架构分层清晰，方便后续接入 AI 和后端。
- 本地优先，隐私安全，用户可删除、可导出。
- 代码可维护、可测试、可持续迭代。

## 4. 大致要求

### 4.1 功能要求

**核心功能 A：推送通知**

- 判断有无智能手表、是否开启健康数据权限。
- 有手表且授权：读取睡眠数据，在醒来时推送记录梦境通知。
- 无手表或不授权：引导用户设置每日定时推送时间。
- 最新入口决定：首次使用通过带菜单图标的一次性引导介绍设置入口；首次进入提醒设置时单独说明通知授权。不反复在每次启动时弹出设置提示。

**核心功能 B：梦境记录**

- 用户能快速进入当日记录窗口。
- 支持自由文本输入、编辑、自动保存。
- 后续可扩展字体大小、文本背景、样式等。

**核心功能 C：日历回顾**

- 用户可通过日历选择日期。
- 查看某天记录的梦境。
- 支持补充记录、编辑已有记录。
- 有记录的日期应有视觉标记。

**Version 0.1 不做：**

- 账号体系、云同步、社交功能。
- AI 画报、周期报告、推荐系统。
- 复杂编辑器、多端同步、付费系统。

### 4.2 体验要求

- 轻：打开快，记录路径短，不打断醒来后的回忆。
- 静：界面安静、克制、有美感，适合清晨和夜晚使用。
- 私：梦境数据高度敏感，默认本地保存，上传需明确授权。
- 稳：通知、保存、日历查询不能频繁失败。
- 可退出：用户可随时删除数据、关闭权限、导出记录。

### 4.3 技术要求

建议技术栈：

| 层级 | 推荐选型 |
|---|---|
| 客户端 | Flutter + Dart |
| 状态管理 | Riverpod / Bloc |
| 路由 | go_router |
| 本地数据库 | Drift / SQLite |
| 通知 | flutter_local_notifications + timezone |
| 健康数据 | health 插件，封装 HealthKit / Health Connect |
| 日历 UI | table_calendar |
| 安全存储 | flutter_secure_storage |
| 导出分享 | share_plus / pdf |
| 后端 | 0.1 可不做；进阶用 FastAPI + PostgreSQL + Redis |
| AI | LLM + 图像生成 API |
| 推荐 | TMDB、Spotify、Open Library 等 |
| 版本控制 | Git + GitHub / GitLab |
| CI/CD | GitHub Actions + Fastlane |

技术原则：

- 本地优先，离线可用。
- 外部服务可插拔，AI 功能后置。
- 健康数据接入优先使用系统统一接口。
- 通知优先本地通知，后台限制严格时再考虑服务端推送。

### 4.4 数据要求

核心数据结构建议包括：

- `DreamEntry`：梦境记录，包含日期、标题、正文、心情、标签、图片、关联睡眠记录等。
- `SleepRecord`：睡眠数据缓存，包含入睡时间、醒来时间、来源设备。
- `UserSettings`：通知时间、权限状态、提醒模式、隐私设置。
- `Report`：后续 AI 报告与画报数据。

数据必须支持：

- 新增、编辑、删除。
- 按日期、按月查询。
- 本地持久化。
- 导出与备份。
- 敏感数据加密或安全存储。

### 4.5 非功能要求

- 隐私合规：明确告知数据用途，健康与梦境数据不默认上传。
- 性能：启动、记录、日历切换应流畅。
- 可用性：无手表用户也能完整使用。
- 可维护性：模块清晰，接口稳定，方便接入 AI。
- 可测试性：核心逻辑、通知、数据层可单元测试。
- 跨平台：iOS 与 Android 行为尽量一致，差异点单独处理。

## 5. 版本规划

### Version 0.1

目标：跑通核心闭环。  
范围：通知、记录、日历。  
验收：双端可运行，权限判断正确，通知正确，文本可编辑保存，日历可查看 / 补记。

### Version 0.2

目标：提升记录体验。  
范围：自动保存优化、导出、统计、心情标签、基础样式。

### Version 0.3

目标：接入 AI 分析。  
范围：周期报告、关键词提取、梦境画报。

### Version 1.0

目标：形成完整产品。  
范围：账号、云同步、推荐系统、多设备、隐私管理。

## 7. 验收标准

Version 0.1 验收标准：

1. iOS / Android 真机可正常安装、启动、运行。
2. 能正确判断健康数据权限与手表可用状态。
3. 有手表时，能在醒来时间附近推送通知。
4. 无手表时，能设置每日定时通知并按时推送。
5. 用户能输入、编辑、保存梦境文本。
6. 日历能正确显示某天记录，支持补记。
7. 无严重崩溃、无数据丢失。
8. 隐私说明、权限说明、删除与导出路径明确。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 健康数据碎片化 | 优先 HealthKit / Health Connect，厂商 SDK 后置 |
| iOS 后台限制 | 本地预排通知，必要时服务端推送 |
| 隐私合规 | 本地优先、明确授权、可删除、可导出 |
| AI 成本与安全 | 限流、缓存、敏感词过滤、用户主动触发 |
| 跨平台差异 | 抽象健康、通知、存储接口，分平台实现 |
| 范围膨胀 | 0.1 严格只做核心闭环，AI 与云同步后置 |

## 9. 协作方式

- 版本控制：Git。
- 分支模型：`main` 为交付主线，按需使用短期 `feature/*` 或隔离 worktree；不要求另设 `dev`。
- 现行流程（2026-11-08）：明确任务 → 开发 → 必要检查 → 更新交接文档 → 本地整合 `main` → `git push origin main`，不默认创建 PR 或等待审核。
- 提交规范：简洁说明功能或修复内容。
- CI：当前自动生成 Drift 代码、检查格式、静态分析和运行测试；不自动修改格式，也尚未执行双端原生构建。平台构建与人工验收单独记录。
- 文档：需求、设计、接口、数据结构持续更新。

---

## 10. 总结

“夜行者 / Morpheus”Version 0.1 的核心不是 AI，而是先做一个稳定、私密、好用的梦境记录工具。

开发目的：在用户醒来时提醒并降低记录门槛。  
最终效果：跑通“醒来提醒 → 记录梦境 → 本地保存 → 日历回顾 / 补记”的闭环。  
大致要求：双端可运行，本地优先，隐私安全，通知正确，记录顺畅，日历可查，架构可扩展。

0.1 做扎实后，再逐步接入 AI 画报、周期报告和推荐系统。
